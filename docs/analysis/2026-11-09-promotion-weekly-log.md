# MynaDB 推广周报与阶段安排

## 初始基线

观察时间及完整字段见 [GitHub API 快照](promotion-evidence/github-public-snapshot.json)。
该快照是公开数据，不包含 Traffic 私有指标。

| 指标 | 初次检查值 | 说明 |
| --- | --- | --- |
| Star | 0 | 只记录基线，不推断增长效果 |
| Fork | 0 | 未将 Fork 当作真实试用人数 |
| Open Issues | 0 | 尚未发布任务草稿 |
| Description / Website | 已设置 | 原计划中的“About 未填写”已过时 |
| Topics | 空 | 已准备主题清单，尚未通过管理接口设置 |
| Release | v0.0.1，无二进制附件 | 不作为预编译包已可用的证据 |
| 独立访客 / 完整 clone | 未获取 | 需要仓库管理者访问 Traffic |
| 外部贡献者 / 独立试用人数 | 未核实 | 不从 Git 提交姓名或 Star 数推断 |
| Quick Start 成功率 | 尚无独立用户样本 | 本次自动化/维护者检查通过，但不能代表独立用户成功率 |

## 每周记录模板

```text
日期及统计时区：

独立访客 / 完整 clone（注明 Traffic 统计区间）：
新增 Issue / 外部贡献者 / PR：
Quick Start 尝试人数 / 成功人数 / 失败原因：
真实使用场景：
本周发布渠道与链接：
流量来源和内容效果：
最常见反馈：
下周优先修复的三个问题：
```

Traffic 展示最近 14 天的访问和 clone 数据，建议每周记录；数据使用 UTC。
参考 [GitHub Traffic 文档](https://docs.github.com/en/repositories/viewing-activity-and-data-for-your-repository/viewing-traffic-to-a-repository)。

## 30 天安排

| 阶段 | 进入条件 | 行动 | 完成证据 |
| --- | --- | --- | --- |
| 第 1 周：基础 | 当前进行中 | 许可证、About、干净源码验证、状态说明和素材 | 检查记录、运行日志、根 LICENSE、配置 |
| 第 2 周：中文首发 | 基础检查通过，完成独立试用 | 技术文章与实际演示，收集反馈 | 发布链接、真实反馈、可复现问题 |
| 第 3 周：英文准备 | 已修复最影响试用的问题 | 更新英文材料，复测后考虑 Show HN | 英文试用记录和问题答复 |
| 第 4 周：复盘 | 有真实反馈样本 | 优先处理三个试用障碍，发布进展 | 修复 PR、复测结果、FAQ |

## 90 天安排

- 第 1–30 天：让陌生用户理解并运行；以许可证、文档和独立试用为检查点。
- 第 31–60 天：补充协议兼容性、WAL 恢复和初步性能基线，公开配置与失败情况。
- 第 61–90 天：整理真实试用案例，发布有证据的 Release、Roadmap 和月度进展。

以上是目标和进入条件，不表示未来几周的执行已经完成。没有流量或试用样本时，
不编造转化率，也不预设某个渠道一定有效。
