# 第二篇编辑与发布说明

## 发布文案

- 通用标题：从零实现一个时序数据库（二）：写入成功之后，如何用 WAL 找回数据
- 知乎备选：时序数据库返回“写入成功”后，如何保证故障时能恢复？
- 掘金备选：手写时序数据库 02：WAL、Checkpoint 与故障恢复
- 摘要：从内存缓冲的数据丢失风险出发，讲清日志追加与同步确认、记录校验、分段轮转、Parquet 提交、checkpoint 和启动重放，并用六张图检查故障发生时的数据归属。
- 建议话题：时序数据库、数据库、Rust（编程语言）；可补充存储系统。

## 内容定位

延续第一篇，围绕 M2 的单机持久化主题讲设计，不逐条复盘历史实现。LSN 与提交清单是为解释恢复边界采用的教学设计，不能作为 v0.1.0 已按此方案实现或已经验证的声明。本文只讨论本地文件系统，未将本地 append、sync 与原子替换语义推广到对象存储。

正文示意代码省略协调器、类型定义和错误处理，未作为可编译应用执行。故障表是建议验证的场景，没有冒充实际测试输出；没有承诺硬件故障下的绝对持久性、客户端重试的 exactly-once 或性能成绩。

## 图文交付

- `article.md`：社区正文，包含第一篇与官方参考资料链接。
- `article.publish.md`：粘贴发布版，图片全部使用 GitHub Pages 的完整 HTTPS 地址，“上一篇”指向在线预览。复制此文件内容，无需逐张替换本地图片路径。
- `preview.html`：本地图文预览。
- `figures/`：六张配图，每张包含 PNG、SVG 和 Mermaid 源文件。
- `build_assets.py`：使用 Pillow、Markdown 和中文字体重新生成配图及预览；字体路径由 `MYNADB_ARTICLE_FONT` 指定。

正文和配图区分四个边界：写入接管、日志同步、Parquet 完成、提交清单发布。有效文件集合与 checkpoint 必须一同提交；只有连续提交范围内的已封口分段可以回收。恢复期间不重新记同一条 WAL，且重放后未提交的数据仍由原 WAL 保护。

## 发布准备

优先使用 `article.publish.md` 粘贴到支持 Markdown 的编辑器。六张图片使用公开直链；这些地址在本次检查时均返回 HTTP 200，远程图片与本地内容一致。重新运行生成脚本会同步更新此发布版。

知乎对 Markdown 和外链图片的解析、转存行为以实际编辑器为准；完整外链不能保证平台一定自动导入图片。发表前确认六张图均在预览中显示，并检查标题、代码块和表格；本文未向知乎或掘金投稿。代码仓库的 commit/push 与社区发布分别记录。
